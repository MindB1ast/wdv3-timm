# Design

## Context

См. proposal.md для мотивации. Существующие `TagMatcher` и `apply_tag_rules` реализуют безусловные списки; `filter_record` применяет их внутри региона. Они не выражают условное наличие apron и не должны получать перегруженный синтаксис в обычных полях тегов. Change `add-scope-local-tag-redundancy` вводит `WDV3_TAG_SETS`, `filter_tag_sets`/`merge_tag_sets`, историю и совместимость цепочек; его контракт является зависимостью этой реализации.

## Goals / Non-Goals

**Goals:** отдельная чистая операция условного удаления; одинаковое поведение на полном кадре и отдельных регионах; проверка правил и сохранение свидетельств каждого срабатывания.

**Non-Goals:** универсальный язык выражений, regex, действия add/replace, автоматическое достраивание dress по отсутствию apron, условия по соседним областям, модельные вероятности в предикатах, TXT-редактор. Более сложные действия требуют отдельного расширения схемы.

## Decisions

### 1. Небольшая версионированная схема

Предлагаемая операция `conditional_remove` содержит `schema_version: 1`, `scope: regions` по умолчанию, `sources: []` (все региональные источники) и `rules: []` по умолчанию. Каждый элемент:

```json
{
  "id": "apron_suppresses_dress",
  "all_of": ["apron"],
  "any_of": [],
  "none_of": [],
  "remove": ["dress"]
}
```

Имена тегов — строки, по одному имени в элементе массива. Существующая канонизация пробелов/`_` применяется к литералам, регистр/пунктуация сохраняются. Не интерпретировать `.*`, скобки и другие символы как regex. Идентификатор непустой и уникальный в операции; дубликаты канонических тегов внутри группы дедуплицируются. Неизвестные поля и неверные типы отклоняются, чтобы опечатка не превращалась в другое правило. Требовать непустой remove и хотя бы одну непустую группу условий. Пустые/отсутствующие группы не накладывают ограничение; для непустых групп действует AND между группами, ALL/ANY/NONE внутри групп. Пустой any_of не означает ложь для всех правил.

Запретить пересечение all_of и none_of и any_of, целиком запрещённый none_of. Условия none_of-only допустимы и проверяются по принятому набору. Действие может удалить собственный свидетель: это пользовательская политика с конечным однопроходным результатом. Альтернатива произвольному Python/выражениям отвергнута как лишняя сложность для данного поведения.

### 2. Набор свидетельств и локальность

Для одного `(image_id, source, region_id)` входной снимок имён — объединение принятых general и character. Схема не меняет категории: remove удаляет точное имя из принятых категорий, где оно присутствует, и не трогает ratings. Сырые теги ниже порога не участвуют. Локальные ручные теги могут быть свидетельствами, если уже приняты фильтрами; это видно в provenance. Финальные prefix/suffix после merge в условия не входят.

Список sources ограничивает только регионы и не расширяет scope на полный кадр. Неизвестные выбранные имена источников — ошибка применения до изменения Bundle, даже если другие источники валидны. Пустой набор регионов выбранного существующего источника — успешная операция без изменений. По полному кадру условие исполняется только при full/all.

При удалении dress из clothes другой регион и full всё ещё могут передать dress в общий caption. Предикат не является глобальным запретом; изменение политики переноса тегов выполняется существующими фильтрами отдельно. Альтернатива проверке уже merged_caption отвергнута: apron одного персонажа подавлял бы dress другого.

### 3. Одно вычисление условий на вход операции

В пределах ноды все правила оцениваются по одному снимку; удаления объединяются, применяются один раз, причины сортируются по стабильному rule ID. Порядок JSON-массива не создаёт скрытой цепочки. Сочетание «apron удаляет dress; dress удаляет skirt» удаляет оба при наличии всех трёх на входе. Противоположные правила `a→remove b` и `b→remove a` также конечны: оба удаляются. В отличие от графа семантической избыточности, такие условия не нуждаются в запрете циклов: нет рекурсивного исполнения и добавлений.

Для последовательной семантики пользователь ставит две ноды; вторая получает выход первой. В том же формате цепочки сохраняется их порядок, включая соседнюю операцию удаления избыточности. Не вводить неявный повтор до устойчивости или приоритет по положению правила.

### 4. Публичная нода и совместимые результаты

Предлагаемая нода `WDV3ConditionalTagRules` принимает tag_sets и поля scope/sources/rules_json, возвращает tag_sets. JSON-поле содержит явную таблицу с примером apron/dress; scope и sources задаются один раз рядом с ней. Принадлежащие генерации поля не копируются. Нода регистрируется в backend preflight и контекстном каталоге: тип подключения совпадает с Remove Redundant Tags, цепочки можно переставлять явно. В перспективе UI таблицы можно добавить поверх того же JSON-контракта без смены вычислительной схемы.

Чистое исполнение не загружает модели и создаёт новый Bundle. В историю каждого удаления записать operation index/digest, rule ID, нормализованные условия, присутствовавшие свидетели, проверки отсутствия, tag/category/score, кадр/источник/регион. Если условий нет/не выполнены, не создавать фиктивное удаление. Raw/evidence/геометрия остаются прежними. Inspect показывает до/после и все причины; merge сохраняет историю в results_json.

Использовать проверку совместимости цепочек и повторное применение из первого change: `merge_results` не должен заменять условно обработанные теги повторной фильтрацией без условий. Политика входит в идентичность постобработки, не raw inference. Постоянный кэш не является зависимостью.

## Risks / Trade-offs

- [Apron и dress могут быть одновременно правильными] → никакого встроенного активного запрета; правило создаёт пользователь, scope виден, удаление объясняется.
- [Пользователь ожидает последовательность строк таблицы] → документация и пример снимка; последовательность выражается отдельными нодами.
- [Тег приходит повторно из full/другой области] → показать происхождение в общем caption и объяснить отдельность существующих фильтров переноса.
- [Невидимая опечатка в правилах] → строгая схема, уникальные ID, канонизация и ранняя проверка постоянных значений.
- [Зависимость от ещё не реализованной стадии] → применять после `add-scope-local-tag-redundancy`, не вводить второй несовместимый тип наборов тегов.

## Migration Plan

После реализации первого change добавить схему/чистую функцию, затем ноду, preflight, Inspect и пример. Пустая операция — тождественное преобразование; старые графы и конфиги не получают условий автоматически. Откат — обход ноды или пустая таблица; прежние исходные оценки позволяют пересобрать теги без моделей.
