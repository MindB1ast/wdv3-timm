# Design

## Context

Мотивация и границы пользовательского результата описаны в proposal.md. Наблюдаемая реализация уже содержит необходимые представления данных.

- comfy_evidence.py разделяет filter_tag_sets и merge_tag_sets. Apply Filters вызывает оба этапа, Filter Tag Sets позволяет вставить операции перед merge.
- DetectorConfig хранит пороги и списки, TagMatcher использует канонические имена и fullmatch regex. None и пустой список full_image_only_tags имеют разные значения.
- comfy_cascade_tags.py сохраняет собственные наборы и aggregate, передаёт origin_candidates снизу вверх, применяет remove/allowed родителя и сохраняет путь кандидата.
- Общий merge проверяет происхождение и подтверждение full. require_full_confirmation сейчас сохраняет тег в регионе. remove_from_full действует при наличии областей. Основные поля описывают разные этапы обработки.
- Scripts/tag_postprocessing.py уже задаёт версионируемую цепочку операций с id, историей и scope. Новая модель должна использовать существующий механизм и тип tag_sets.
- add-child-tag-subtraction описывает pending removals и отдельный готовый маршрут. Его implementation-задачи остаются в исходном change. При применении изменений в любом порядке требуется согласованная семантика subtract.

## Goals / Non-Goals

**Goals**

- Один декларативный контракт для выбора тегов и выполнения действий над рабочими наборами и вкладом в caption.
- Настраиваемые связи full/parent/children без изменения области детекции и без повторного инференса.
- Эквивалентные готовые фильтры, детерминированные результаты и воспроизводимые пользовательские примеры.

**Non-Goals**

- Исполнение пользовательских скриптов, формулы над произвольными Python-объектами и новые inference-стадии.
- Автоматическое установление родства независимых областей или семантическая классификация совпадающих bbox.
- Усреднение моделей и калибровка вероятностей. Новое score-правило выбирает существующую оценку либо явно назначенную ручную.

## Decisions

### 1. Декларативная операция с фиксированными полями

Предлагается schema_version=1 с полями id, enabled, phase, anchors, source, target, tags, condition, action и score_policy. Составные условия представляются деревом all/any/not над проверками tag_present, tag_absent, score_above и regions_exist. Экспорт использует JSON того же контракта. UI собирает объект из обычных полей, выбора условия и связанной цепочки, скрывая неактуальные настройки.

Названия нод для реализации предлагаются как Custom Tag Rule, Combine Tag Rules и Apply Tag Rules. Первая строит одно правило и может принять previous_rules, вторая объединяет независимые цепочки в порядке входов, третья принимает tag_sets и возвращает tag_sets. Если для составного условия нужна отдельная нода Tag Rule Condition, она входит в тот же scope и должна иметь собственную демонстрацию. Точные display_name можно уточнить при реализации без изменения контракта.

Декларативные поля позволяют проверять конфиг до исполнения и показывать причину конкретного изменения. Альтернатива с произвольным кодом не даёт проверяемой совместимости и не нужна для обсуждённых операций.

### 2. Экземпляр области как точка отсчёта

Anchors выбирает области, для которых исполняется правило. Подключённая к Region Tag Rules цепочка получает self соответствующего источника. Самостоятельная операция задаёт anchors через full/regions, имена источников и depth. Источник и цель разрешаются по self, parent, children, descendants, full и caption. Для нескольких выбранных источников кандидатные теги объединяются с сохранением всех origins.

Идентичность задаётся image_id и region_uid, связи берутся из parent_region_uid. Источник имени person/person отличается от person. На плоских старых данных без дерева доступны self/full и выбор существующих источников для anchors, parent пропускается с объяснением. Выбор parent никогда не выводится из совпадения region_id или геометрического пересечения.

Источник reading_set выбирает own или aggregate. Local читает текущие рабочие наборы до маршрутизации. После завершения local создаётся неизменный own_snapshot для сравнений в aggregate/caption. Этот снимок отражает основные и кастомные локальные фильтры. Последующие изменения рабочего own при переносе сохраняются отдельно от own_snapshot и исходных raw_scores.

### 3. Алгебра выбранной части набора

Пусть F выбирает теги по категории и literal/regex, S является выбранной частью источника, T выбранной частью цели, U остальными тегами цели.

| action | Новая цель |
| --- | --- |
| union | U ∪ T ∪ S |
| subtract | U ∪ (T ∖ S) |
| intersect | U ∪ (T ∩ S) |
| replace_selected | U ∪ S |
| copy | union без изменения источника |
| move | union и удаление только успешно принятых тегов из рабочего источника |
| add_literal | union с явно заданными тегами и ручными оценками |
| threshold | U плюс элементы T со score строго выше порога |

Copy предоставляется в интерфейсе как понятное название union с сохранением источника, а не отдельная математическая операция. Удаление по literal использует выбранные теги как явно заданное множество. Пустой literal/regex при tags.mode=selected выбирает ноль тегов, tags.mode=all выбирает всю выбранную категорию.

При intersect с пустым найденным множеством source выбранная часть цели очищается. Если требуемого parent нет, весь экземпляр правила пропускается. Отсутствие областей children является пустым множеством. Квантор all требует непустую выборку. Неверное имя объявленного источника является ошибкой, ноль его детекций является корректным случаем.

### 4. Ограничения получателя и происхождения

Кастомная цепочка исполняется после соответствующих основных локальных правил. Добавленный или переданный тег повторно проходит ограничения remove/allowed/full_image_only получателя и политики владельцев. Эти ограничения сохраняют силу и после ручного добавления. Для move отказ получателя сохраняет тег у источника.

Caption поддерживает две явные цели. Contribution изменяет допуск выбранных кандидатов и сохраняет записи регионов. Final caption изменяет общий набор после разрешения вкладов. Для него запрещены чтение несуществующего parent и перенос из строки текста. Общий текст заново формируется из структурированного набора. Правила происхождения проверяются при обеих целях, пересылка через родителя сохраняет origin_source.

### 5. Порядок и конфликтующие изменения

Этапы выполняются в порядке local, aggregate, caption. В local цепочка исполняется в указанном порядке на собственных наборах. Затем фиксируется own_snapshot и строятся начальные агрегаты.

Aggregate проходит depth от глубоких уровней к корню. На каждом уровне цепочка выполняется по порядку. Все экземпляры одного правила на этом уровне читают один снимок и формируют пакет изменений. После успешной проверки пакета добавления объединяются, удаления выигрывают в пределах этого шага, а затем начинается следующее правило. В явной последовательности правило 2 может добавить тег, удалённый правилом 1, если это разрешено постоянными ограничениями.

После кастомных aggregate-правил уровня выполняется штатная передача отдельными маршрутами separate/merge_to_parent. Благодаря этому родительский уровень видит результаты детей, а own_snapshot родителя сохраняет его собственное распознавание. Одновременное явное union и merge_to_parent допустимо с устранением дублей и сохранением происхождения. В демонстрациях используется separate с явной передачей, чтобы одно действие объяснялось одним правилом.

Для будущего subtract_from_parent сохраняется его контракт pending removals после всех sibling-вкладов. Его готовый пресет компилируется в тот же пакет удаления, который использует кастомное правило. Реализация самого маршрута остаётся в связанном change.

Caption-цепочка выполняется один раз после завершения дерева. Условие подтверждения own читает снимок до передачи детей, условие aggregate читает снимок начала текущего правила. Полная цепочка создаёт новое значение Bundle и при ошибке не публикует частичный результат. Накопление изменений при повторном применении исключается пересборкой из сохранённого базового входа и заменой плана операций.

Альтернатива с произвольным обходом дерева была отвергнута, поскольку одинаковый конфиг мог бы менять результат при перестановке соседних детей.

### 6. Политики оценок и сохранение origins

Max выбирает максимальную существующую оценку, keep_target сохраняет оценку цели при совпадении и берёт source при новом теге, take_source выбирает оценку source. Если source включает несколько областей, среди source используется максимум. Равные кандидаты упорядочиваются по origin_source и region_uid, при этом все origins сохраняются. Subtract/intersect не меняют оценки оставшихся тегов цели. Add_literal хранит assigned_score отдельно от model_score.

Категории general и character независимы. Ratings сохраняются отдельно. Наборы с неполными оценками могут использовать операции над наличием тегов, а score-условия требуют реальную доступную оценку и дают ошибку capabilities при её отсутствии.

### 7. Основные настройки как готовые рецепты

| Основное поле | Представление в общем контракте |
| --- | --- |
| general_threshold / character_threshold | local, self, threshold по категории |
| remove_from_regions | local, self, вычитание literal/regex |
| allowed_tags | local, self, пересечение с разрешёнными именами |
| add_to_regions | local, self, add_literal |
| require_full_confirmation | caption contribution этого источника, tag_present в full.own |
| remove_from_full | caption contribution full, regions_exist данного источника, запрет выбранных тегов |
| only_from_source | политика допуска origin_source с объединением объявленных владельцев |
| full_image_only_tags | объединённое по источникам ограничение региональных own/aggregate и допуск caption только от full |
| regex-поля | тот же рецепт с полным совпадением канонического имени |

Full_image_only сохраняет текущие defaults, None/[] и объединение ограничений всех источников. Allowed_tags пустого основного поля сохраняет прежнее значение «без ограничения», хотя явный кастомный intersect с пустым множеством очищает выбранную часть. Компилятор готового рецепта обязан отразить это различие.

Пользователь может получить отключённую кастомную копию готового рецепта и сравнить её в отдельной ветке, отключив основное поле. Параллельный эксперимент использует одни оценки. Замена старой реализации общим движком допускается после таблицы эквивалентности всех полей и существующих regression-тестов. Возможен промежуточный адаптер с прежним backend.

### 8. Интеграция с существующей постобработкой

Расширяется существующая цепочка Scripts/tag_postprocessing.py. Region Tag Rules получает optional custom_rules в конце схемы. Самостоятельный Apply Tag Rules регистрирует план в tag_sets, local исполняется на локальной стадии, aggregate/caption исполняются Merge Tag Sets либо внутренним merge у Tag Image / Regions и Tag Folder. Inspect локальной стадии показывает выполненный local и ожидающие последующих этапов правила. Apply Filters исполняет правила, сохранённые в evidence, либо полученные через полный совместимый набор overrides.

Remove Redundant Tags сохраняет действующую локальную семантику. Свободная перестановка её между aggregate/caption не включается автоматически в этот change. Пресеты и цепочки передают явные этапы, новый контракт не меняет meaning существующего scope.

Rules участвуют в хеше обработанного результата. Ключи raw inference определяются моделями и геометрией, поэтому новые фильтры повторно используют те же оценки. Входные pix/маски и строки raw_scores сохраняются. Сериализатор конфигов проверяет версию и поддерживает старые данные без custom_rules.

### 9. Демонстрации как исполнимый контракт

Набор fixtures содержит фиксированные модельные оценки с понятными тегами, полным кадром, двумя родителями и детьми до третьего уровня. Для каждого основного фильтра сохранены отдельные базовая и изменённая ветки и кастомный эквивалент. Для каждого нового действия и ноды есть пример с комментариями, собственным набором, aggregate и caption, фиксированными assertions и командой запуска.

Сравнение выполняется по image_id/region_uid, категории и ожидаемому происхождению, а не по порядку регионов или одной строке caption. Отдельно проверяются formatted tags и компактный JSON. Исходные fixtures и эталоны никогда не перегенерируются при обычном запуске. Реальные saved-workflow regressions из audit сохраняются и выполняются при приёмке, дополняя независимые от моделей демонстрации правил.

## Risks / Trade-offs

- Неправильная эквивалентность готового фильтра → фиксированные пары basic/custom для каждого поля, пустых значений, regex и конфликтов.
- Самоподтверждение или перенос между соседними объектами → снимок own и тесты двух родителей с одинаковыми локальными region_id.
- Дублирование custom union и merge_to_parent → сохранение origins, устранение дублей и показ обоих путей в истории.
- Рост служебных данных → история содержит фактические изменения и отказы выбранных кандидатов, без копирования полного WD-словаря на каждом правиле.
- Конфликт с другими changes → adapter-тесты отдельно фиксируют контракт subtract_from_parent и существующих операций постобработки.
- Много настроек в одной ноде → готовые рецепты, краткие подписи цели и этапа, скрытие неприменимых полей при сохранении API-валидации.

## Migration Plan

1. Добавить контракт и детерминированные операции с проверками на фиксированных наборах.
2. Подключить обработку tag_sets, каскад, caption и объяснимое происхождение.
3. Добавить UI и переносимые конфиги с optional-полями, сохранив старые keys и индексы выходов.
4. Проверить все basic/custom пары до перевода готовых полей на общий backend. Старый backend может остаться адаптером, если сохраняет единый контракт.
5. Выполнить демонстрации и regression-набор. Откат выполняется отключением custom_rules в сохранённом конфиге, исходные raw-артефакты остаются пригодными для прежней обработки.
