# Design

## Context

Мотивация и объём: [proposal.md](proposal.md). `BatchTagging` связывает файловый ввод, загрузку моделей, инференс, фильтрацию и сохранение. `tag_image` возвращает только прошедшие порог теги; региональные словари меняются раньше текстовых полей. Детекция принимает путь файла, хотя YOLO может работать с изображением в памяти. `merge_tags_from_regions` перезаписывает исключения полного кадра и хранит глобальный список внутри функции. Импорт `Scripts` сразу импортирует также notebook-аналитику.

Последний прогон: WD ViT v3, 448×448, CPU; человек и лицо работают, но `helmet` приходит из лица, а пустая ветвь лица может удалять `eyelashes`. Эти случаи нужны для проверки причин решений, а не только конечного списка. Установленный для прогона Python 3.11 находится в `temp` и не является окружением ComfyUI. Путь к пользовательской установке ComfyUI ещё не указан; создание плана этого не требует.

## Goals / Non-Goals

**Goals:** независимые вычислительные этапы с типизированными данными; визуальные настройки без обязательного редактирования JSON; просмотр любого этапа; повторное применение правил к сохранённым оценкам; готовый небольшой граф и машиночитаемый результат.

**Non-Goals:** собственный графовый редактор, перенос всей исследовательской системы, внешний сервис или отдельная БД. Одно изображение (`B=1`) за исполнение — явная граница MVP; множество областей обрабатывается последовательно. Расширение не изменяет изображение, не определяет объектные экземпляры и не объединяет атрибуты в составные названия.

## Decisions

### 1. Пакет custom nodes и независимые вычисления

Устанавливаемая единица — этот репозиторий как пакет в `ComfyUI/custom_nodes/wdv3-timm` с корневой точкой регистрации, тонкими адаптерами в `comfyui_nodes/`, frontend в `web/`, примерами в `examples/comfyui/`. Существующие `Scripts` остаются импортируемыми для ноутбуков. Выделить чистые операции обработки изображения, получения вероятностей и применения правил, исключив импорт notebook-аналитики при загрузке расширения.

Использовать документированный V1-контракт регистрации нод и `WEB_DIRECTORY` для небольшого расширения UI: официальная документация подтверждает его поддержку. Конкретные проверенные версии backend/frontend ComfyUI зафиксировать при реализации и указать в документации совместимости. Не переключаться на приватные интерфейсы ради виджетов. Альтернатива — V3 API — допустима отдельной миграцией; она не нужна для первого набора нод.

Не оборачивать `BatchTagging` одним большим узлом: тогда настройка фильтра потребует повторного инференса, а промежуточные выходы останутся скрытыми. Не копировать вычисления в отдельную реализацию для ComfyUI.

### 2. Каталог нод

Все идентификаторы имеют префикс `WDV3`, отображаемые имена — префикс `WD`; категория меню `WD Regional Tagger`.

| Нода / ID | Входы и настройки | Выходы |
|---|---|---|
| **Load WD Model** / `WDV3LoadTagger` | Модель из `models/wd_taggers`, устройство `auto/cpu/cuda`, разрешение скачивания выключено по умолчанию | `WD_TAGGER`: модель, словарь, предобработка, метаданные |
| **Load YOLO Model** / `WDV3LoadDetector` | Модель из `models/wd_detectors`, устройство, явное разрешение скачивания | `WD_DETECTOR` |
| **Detect Regions** / `WDV3DetectRegions` | `IMAGE`, детектор, уникальное имя источника (`face`, `person`), confidence, классы | `WD_REGIONS`, диагностический `WD_RESULT` |
| **Tag Image** / `WDV3TagImage` | `IMAGE`, `WD_TAGGER` | `WD_EVIDENCE` полного кадра; оценки до порога |
| **Tag Regions** / `WDV3TagRegions` | `WD_REGIONS`, тот же либо другой `WD_TAGGER` | `WD_EVIDENCE` областей; оценки до порога |
| **Filter Rules** / `WDV3FilterRules` | Пороги, списки правил, preset, режим отсутствующего источника | `WD_RULES` |
| **Apply Filters** / `WDV3ApplyFilters` | `WD_EVIDENCE`, `WD_RULES`, опциональный результат полного кадра для подтверждения региональных тегов | `WD_RESULT` с принятыми и отклонёнными кандидатами |
| **Merge Results** / `WDV3MergeResults` | Два `WD_RESULT` — одиночные ветви или уже объединённые результаты | `WD_RESULT`, итоговая строка `STRING` |
| **Inspect** / `WDV3Inspect` | `WD_REGIONS`, `WD_EVIDENCE` или `WD_RESULT` через три необязательных типизированных входа; заметки пользователя | UI отчёта, изображение с рамками `IMAGE`, текст `STRING`, отчёт с фидбеком `WD_REPORT` |
| **Export Report** / `WDV3ExportReport` | `WD_REPORT`, префикс имени, флаги JSON/HTML/TXT | Пути созданных файлов `STRING` и UI-ссылки |

Отдельный загрузчик изображений не нужен: используется штатный `LoadImage`, выход `IMAGE`. `MASK` из него в MVP не используется. `Inspect` можно подключить в нескольких точках графа. Он не меняет входные вычислительные данные; пометки входят только в отчёт. Экспорт — отдельная output-нода, чтобы вычисления не изменяли TXT автоматически.

### 3. Готовый workflow

```text
LoadImage --> Tag Image ----------------------> Apply Filters (full) ----+
                 ^                                  ^                  |
Load WD Model ---+                             Filter Rules             |
       |                                                               v
       +-------------------------------------+                    Merge Results --> Inspect --> Export
                                             |                         ^
LoadImage --> Detect Regions --> Tag Regions -+--> Apply Filters -------+
                  ^                                   ^
Load YOLO Model --+                               Filter Rules
```

В примере две региональные ветви: человек и лицо. Дополнительная ветвь подключается ещё одним `Merge Results`. Для `require_full_confirmation` соответствующая региональная `Apply Filters` получает результат `Apply Filters (full)`. `Merge Results` объединяет сохранённые ветви и пересчитывает финальные решения из них: преждевременное исключение тега в первом merge не теряет его исходные свидетельства.

Граф без регионов также работает: полный кадр → фильтры → просмотр. Одна региональная ветвь не обязана иметь найденные области, чтобы вернуть валидный пустой результат.

### 4. Данные и координаты

`IMAGE` — RGB tensor `[1,H,W,3]`, значения 0..1. Проверять `B=1`, не брать молча только первую картинку. Конвертация в PIL не меняет ориентацию и размер; RGB→BGR выполняется только в подготовке входа WD, как в текущем коде. YOLO получает изображение в памяти, без временного сохранения JPEG.

Контейнеры версионированы и не изменяются downstream:

- Идентификатор изображения определяется содержимым RGB-пикселей и размером, а не именем файла. Источник кадра `full`, имена региональных источников уникальны в графе этого изображения.
- `WD_REGIONS`: идентификатор изображения, исходные размеры и пиксели/ссылка в памяти, модель и параметры детекции, для каждого региона `region_id`, класс, confidence, bbox `[x1,y1,x2,y2]`, вырезка исходного разрешения. Ошибочные боксы диагностируются; координаты ограничиваются размером изображения.
- `WD_EVIDENCE`: категория, канонический тег, исходный score до порога, ссылка на источник и регион, сведения о модели и предобработке. Общие, персонажные и рейтинговые оценки не смешиваются.
- `WD_RULES`: снимок порогов и правил с версией. Поиск тегов и сравнение используют единое каноническое имя с подчёркиваниями; пробелы во вводе нормализуются. Не менять смысл пунктуации тегов.
- `WD_RESULT`: стадия, исходные свидетельства, кандидаты, применённые правила и причины, bbox/вырезки, принятые теги и форматированный текст. Для стадии детекции теги отсутствуют; инспектор показывает геометрию и диагностику. Merge принимает только стадию после фильтров либо merge.
- `WD_REPORT`: сериализуемые данные результата, идентификатор содержимого результата, UI-данные и отдельный пользовательский фидбек. Не содержит веса моделей.

Регионы разного размера хранятся как коллекция внутри одного контейнера, а не склеиваются в IMAGE batch с растяжением. Сводная контактная таблица — только визуализация; оригинальные вырезки доступны отдельно.

### 4.1. Точка расширения для кастомных классификаторов и VLM

Общий контракт адаптера отделяет выделение областей от получения описания.
Адаптер объявляет идентификатор/версию модели, предобработку, параметры и тип
результата: `tag_scores`, `class_label` или `text`. Его вход — полный кадр либо
одна область выбранной YOLO/SAM-ветви; назначение выполняется связями графа.
Допускаются несколько адаптеров на одной области и повторное использование
одного адаптера для разных областей. WD — первый рабочий адаптер MVP.

В контракте свидетельств предусмотреть необязательные текстовые записи:
`text`, `output_kind`, `image_id`, `source_id`, необязательный `region_id`,
`model_id`, `model_version`, настройки инференса и необязательный score.
Для VLM сохранять также prompt и параметры генерации. Классификатор преобразует
класс в текст адаптером; необработанные поля ответа при необходимости сохраняются
как метаданные. Отсутствующий score не заменять на 1.0 или иное число.

Существующие записи WD_EVIDENCE с general/character/rating и исходными scores
сохраняют свою семантику. Канонизация Danbooru, пороги и merge по максимальному
score относятся к таким записям; свободный текст сохранять отдельно без замены
пробелов, разбиения по запятым и автоматического применения теговых фильтров.
Для превращения текста в теги нужен явно заданный адаптер/этап. Просмотр и
JSON-экспорт должны иметь документированное расширение для текста и его
происхождения; автоматическое построение единого caption из VLM-текстов пока
не определено.

В текущем change проектируется этот контракт и проверяется переносимость
текстовой записи без score. Новые ноды загрузки/инференса классификаторов и VLM,
поддержка геометрии SAM и конкретные схемы их объединения относятся к следующему
этапу. Наличие контракта не означает, что эти backend уже поддержаны.

### 5. Интерфейс правил

Основной режим `Filter Rules` — обычные виджеты ComfyUI: числовые пороги, выбор пресета и многострочные поля с тегами через запятую либо по одному в строке. Подписи и подсказки объясняют последствия. JSON остаётся форматом переноса и API, а не обязательным пользовательским интерфейсом.

Поля региональной ветви:

| Поле UI | Смысл / соответствие |
|---|---|
| General / Character threshold | Отсечение по категории, сравнение `score > threshold`, как сейчас |
| Remove from region | `remove_tags_from_region` |
| Add to region | `tag: score`, проверка диапазона 0..1; источник решения `manual_rule` |
| Suppress full-image tags when regions found | `remove_tags_from_full`; применяется при merge только для непустого источника |
| Require full-image confirmation | `exclude_from_region`; тег региона допускается только если он прошёл пороги/фильтры ветви полного кадра |
| Full-image-only tags | Список композиционных тегов, запрещённых для добавления из этой региональной ветви; preset содержит текущий глобальный список |
| Only from this source | Теги, для которых эта ветвь объявляет исключительный источник |
| Missing-source behavior | `omit` либо `allow_full`; явный fallback для исключительных тегов |

Для полного кадра доступны пороги, remove/add; региональные поля визуально отключены. Тип области определяется входными свидетельствами, а не произвольным несогласованным переключателем. Виджет правил может иметь выбор `full/region` только для настройки; `Apply Filters` проверяет совпадение с входом.

Presets: `Full image`, `Generic region`, `Person`, `Face`, `Custom`. `Person` и `Face` переносят имеющиеся правила из `detectors.json`; UI явно показывает их содержимое, включая сомнительные правила, вместо скрытого исправления. Импорт кнопкой «Import detectors.json» читает выбранный пользователем файл в браузере и переносит правила выбранного детектора в виджеты. Параметры YOLO/model_path показывает отдельно для переноса в ноды загрузки/детекции; они не изменяют чужие ноды скрытно. Экспорт пресета и workflow сохраняет полный снимок значений. В API те же значения передаются обычными входами.

Если теги добавлены вручную, они помечаются как добавленные правилом; значение не называется вероятностью модели. Подсказка для «исключительного источника» предупреждает, что правила касаются тегов полного изображения, а не выбора одного из нескольких одинаковых объектов.

### 6. Порядок решений и merge

1. Порог соответствующей категории; затем локальные remove, принудительные add и региональные ограничения. Явный remove имеет приоритет над add; конфликт виден в диагностике.
2. Подтверждение полного кадра использует принятый набор ветви `full`. Если поле задано, но эта ветвь не подключена к `Apply Filters`, вернуть понятную ошибку.
3. При merge собрать все уникальные источники и правила. Источники разных изображений и разные версии одной ветви не объединять; повтор одинаковой ветви не дублирует результат.
4. Теги `Only from this source` принимаются только из объявленной ветви. При пустой ветви `omit` удаляет альтернативные источники; `allow_full` разрешает свидетельства полного кадра. Несколько разных владельцев одного тега — ошибка конфигурации, а не выбор по порядку соединений. Если регионы найдены, но тег не прошёл их правила, fallback отсутствующего источника не применяется.
5. Объединить исключения полного кадра всех непустых региональных ветвей. Пустая ветвь сама по себе ничего не удаляет; исключительное владение из шага 4 — отдельное явное правило.
6. Для каждого тега категории general/character выбрать максимальный разрешённый score, сохранив все источники и решения. Значения ratings брать из полного кадра. При отсутствии `full` региональный просмотр разрешён, но экспорт итогового глобального описания требует полного кадра.
7. Сформировать `caption`, `taglist`, `general`, `character` из одного принятого набора. Поведение не зависит от порядка ветвей. Не удалять автоматически семантические обобщения и не объединять несовпадающие категории.

Изменения исправляют известные дефекты, а не обязаны побитово воспроизводить их. Для notebook-пути сохранить публичную сигнатуру и формат `(all_results, all_merged_results)`; корректность правил проверить на общей вычислительной реализации, а не поддерживать два разных merge.

### 7. Загрузка моделей и повторное исполнение

Зарегистрировать каталоги через ComfyUI `folder_paths`: `wd_taggers` для наборов config/labels/weights и `wd_detectors` для YOLO. Существующие папки можно подключить через стандартные дополнительные пути моделей, без копирования больших весов. Preset моделей WD покрывает текущий `MODEL_REPO_MAP`; произвольный remote code не требуется.

Локальная загрузка WD строит архитектуру по локальному config и загружает веса без обязательного обращения `timm.create_model('hf-hub:...')` к сети. Если модели нет, loader объясняет ожидаемые файлы. Явный `allow_download` разрешает скачивание выбранного известного набора в зарегистрированный каталог с прогрессом; скачать только один формат весов. CPU поддерживается; `auto` использует доступное устройство, явный недоступный `cuda` вызывает ошибку. Операции должны соблюдать прерывание ComfyUI и освобождать ресурсы при смене модели; возможности штатного model management переиспользуются через адаптер.

Инференс-ноды не принимают фильтры и пороги: при их изменении ComfyUI использует upstream-кэш и выполняет только дешёвые этапы. Fingerprint загрузчика учитывает конфиг, словарь и изменение файлов весов, детекция — модель/параметры/изображение. Политика кэша между перезапусками сервера в MVP не реализуется. Отдельный общий реестр кэша моделей с неограниченным удержанием GPU не создаётся.

### 8. Инспектор и фидбек

Небольшое frontend-расширение добавляет к `Inspect` просмотр рамок и вырезок, переключатель источника/региона и таблицу `tag | category | score | source | status | reason`. Режимы: принятые, отклонённые, все; для больших исходных векторов — поиск и пагинация. Это не тысячи строк, автоматически отрисованные на canvas.

Фидбек: пользователь выбирает тег и источник, статус `correct/incorrect/uncertain`, комментарий либо вручную указывает пропущенный тег. Каждая запись связана с идентификатором результата, кадра и региона. Сохраняется как сериализуемое поле ноды в workflow; `Inspect` при повторном выполнении возвращает его в `WD_REPORT`, затем `Export Report` сохраняет в JSON. После изменения виджета требуется Queue для обновления выходов; UI это показывает. Фидбек для другого результата не переносится незаметно: показывается как устаревший и не включается как актуальный. Фидбек не обучает и не меняет фильтры автоматически.

В API Inspector возвращает тот же сериализуемый отчёт без обязательного браузерного callback. Выход `IMAGE` позволяет пользоваться штатным `PreviewImage`; `STRING` — копировать caption в другие ноды. Сравнение с эталонами датасета и вычисление метрик вне объёма первого инспектора.

### 9. Экспорт, установка и совместимость

`Export Report` записывает выбранные форматы в подкаталог output ComfyUI с уникальным идентификатором запуска: JSON с происхождением и фидбеком, HTML с локальными изображениями/вырезками и таблицами, TXT итогового caption. Предикты не пишутся рядом с исходным изображением, существующие файлы не перезаписываются. Теги и комментарии экранируются в HTML. Модели в экспорт не включаются; версия схемы и настройки включаются.

Отдельный минимальный список зависимостей расширения не закрепляет `torch==2.6.0`, pandas/IPython и notebook-стек поверх ComfyUI. Совместимые версии timm/ultralytics/HF/safetensors определяются и фиксируются по smoke-прогону в окружении выбранной поддерживаемой версии ComfyUI. Начальная референсная платформа Windows; в документации отличать проверенное от предполагаемой переносимости. Публичное размещение в Registry и установка ComfyUI пользователю не входят в этот change.

### 10. Основания выбора

- [Архитектура custom nodes](https://docs.comfy.org/custom-nodes/overview): Python-узлы и API-запуск графа позволяют отделить вычисления от интерфейса.
- [Контракт V1 и кэш](https://docs.comfy.org/custom-nodes/backend/server_overview): поддерживаемые входы/выходы и пересчёт при изменении входов.
- [IMAGE и пользовательские типы](https://docs.comfy.org/custom-nodes/backend/datatypes), [списки и batches](https://docs.comfy.org/custom-nodes/backend/lists): отдельный контейнер регионов избегает смешения списка вырезок с tensor batch.
- [Штатные LoadImage и PreviewImage в исходниках](https://github.com/Comfy-Org/ComfyUI/blob/master/nodes.py): повторное использование стандартного ввода/просмотра.

Это ссылки на основания плана, проверенные 2026-10-29; совместимость конкретной установки устанавливается smoke-прогоном, а не датой документации.

## Risks / Trade-offs

- [Frontend ComfyUI меняется] → небольшой UI, сериализация через публичные механизмы, точные проверенные версии и API-путь без браузера.
- [Полные вероятности и множество вырезок увеличивают память] → компактные массивы CPU, ленивое форматирование/пагинация, последовательный инференс регионов и освобождение временных tensors.
- [Два разных фильтра претендуют на один тег] → ошибка конфигурации с именами источников вместо молчаливого приоритета.
- [Изменение legacy merge меняет старый результат] → отдельно документированные исправления, проверки пустого лица/порядка ветвей и совместимости формата notebook.
- [Расширение можно принять за готовую систему описания объектов] → в UI и README прямо указывается: это региональные свидетельства и теги, без установления экземпляров и пространственного описания.
- [Старый фидбек применяется к новому запуску] → связь с fingerprint результата и явное состояние устаревшей записи.

## Migration Plan

1. Выделить проверяемое вычислительное ядро, сохранив notebook API и текущие конфиги.
2. Добавить регистрацию пакета, loaders, поэтапные ноды и базовый workflow; затем UI и экспорт.
3. На тестовой установке ComfyUI зафиксировать backend/frontend/Python/torch и проверить CPU-путь, API и интерактивное восстановление workflow. GPU-проверку выполнять при наличии устройства и обозначить её результат отдельно.
4. Пользователь подключает существующие веса и импортирует готовый workflow. Старые ноутбуки сохраняются.
5. Откат расширения — удалить/отключить пакет custom nodes и вернуть предыдущую версию репозитория; исходные изображения, TXT и модели не мигрируются разрушительно. Экспорты остаются самостоятельными файлами.

## Open Questions

- Путь и версия пользовательской установки ComfyUI нужны для проверки именно её окружения; разработку и автоматические проверки можно выполнять на отдельной зафиксированной установке.
- Язык подписей UI и внешний вид таблицы можно уточнить при просмотре прототипа; типы данных и поведение от этого не меняются.
