# Design

## Context

Мотивация и границы — в `proposal.md`. Сейчас `MODEL_REPO_MAP` содержит пять aliases SmilingWolf. `Scripts/main.py` и `WDModelLoader` отдельно создают timm transform через `resolve_data_config`. Поэтому фиксированного общего resize в этих загрузчиках нет, но полного контракта разных семейств тоже нет: `tag_image` и `RegionTagger.score_batch` независимо добавляют квадратный padding и меняют каналы уже преобразованного tensor на BGR.

`Scripts/model.py` сохраняет модели по последнему компоненту repo ID, не скачивает `preprocess.json`, подавляет все `HfHubHTTPError` при скачивании и может пробовать оба формата весов. ComfyUI отдельно требует три файла и отслеживает их изменения. Формат `LabelData` уже поддерживает категории 0/4/9, но полный кадр не проверяет соответствие длины выхода CSV. `RegionTagger` используется также ComfyUI и повторным тегированием сохранённых областей: это точка общего inference.

Существующая `regional-tag-optimization` уже требует определять разрешение по конфигурации в вводном разделе. Новый профиль конкретизирует этот принцип, не меняя целевые требования пространственного описания. Дельта ComfyUI сохраняет оба существующих сценария загрузчика.

## Goals / Non-Goals

**Goals:** Один resolver ресурсов и один callable preprocessing с явным сериализуемым профилем. Сохранить внешний `ImageTransform` и `WDV3_MODEL`, чтобы новые семейства не создавали отдельные ветки регионального inference. Хранить форму как `(C,H,W)`, отдельно от размера исходной вырезки и batch size.

**Non-Goals:** Автоматическое выполнение кода из репозитория модели, новый ONNX backend, одновременный ensemble, изменение merge/порогов и автоматическое обновление каталога через сеть при каждом старте.

## Decisions

### 1. Каталог и прямой repo ID

Ввести общий resolver идентификатора: старый alias или полный repo ID → описание модели и семейство профиля. `MODEL_REPO_MAP` оставить совместимым представлением прежних aliases. Notebook принимает repo ID в существующем `model`; ComfyUI сохраняет dropdown и добавляет необязательный repo ID с явным приоритетом над dropdown. Добавлять поле в конец optional inputs для старых workflow. Поддержка прямого ID не равна поддержке произвольной архитектуры: совместимость проверяется по доступным timm-ресурсам, входному профилю и multi-label словарю.

Встроенный список формируется из объединения опубликованных timm-теггеров SmilingWolf, AnimeTimm `dbv4-full` и ranklist. Никакого scraping при inference. Каталог хранит происхождение и дату проверки; отсутствующие/несовместимые модели перечисляются в документации с причиной, а не предлагаются как рабочие. Старые ONNX/TensorFlow-only WD v2 не требуют отдельного backend в этом change. Иные семейства AnimeTimm (e621, pexels, single-label) не добавляются по одному лишь автору.

Проверенные источники на 2026-11-02:

- [SmilingWolf](https://huggingface.co/SmilingWolf): пять имеющихся WD v3 timm моделей; остальные релизы нужно классифицировать по наличию совместимых файлов.
- [AnimeTimm](https://huggingface.co/animetimm): есть более новые `convformer_s36.dbv4-full`, `convformer_b36.dbv4-full`, `repvit_m2_3.dbv4-full`, `vit_giantopt_patch16_siglip_384.dbv4-full`, `eva_giant_patch14_560.dbv4-full`, которых нет в историческом ranklist. Их размеры не угадывать по именам.
- [ranklist.csv](https://huggingface.co/spaces/animetimm/dbv4-full-ranklist/blob/main/ranklist.csv): 21 строка; дополнительно к двум контрольным моделям содержит caformer s18/s36/m36, ConvNeXt base, EVA02 large, SwinV2 base, ViT base, MobileNetV3/V4, MobileViT и ResNet. В частности, `vit_base_patch16_224.dbv4-full` имеет вход 448, а вариант MobileNet `.r224` — отдельный repo ID. Полный список нужно зафиксировать в проверяемом manifest при реализации.

Альтернатива — расширять только aliases — сохраняла бы постоянную необходимость править код при выпуске модели и не решала бы preprocessing.

### 2. Полный входной профиль

Ввести профиль с `input_size=(C,H,W)`, layout CHW/NCHW, dtype, диапазоном пикселей, порядком каналов, ordered operations, mean/std, interpolation/antialias, padding/background и источником метаданных. Эффективный профиль имеет канонический JSON и fingerprint; отсутствие операции фиксируется явно.

- AnimeTimm: читать `preprocess.json['test']` как основной источник операций. Архитектуру и параметры classifier брать из `config.json`. Сверять выходную форму preprocessing с конфигурацией модели; конфликт диагностировать. Сохранять все операции и их порядок, включая отличия PadToSize от существующего `pil_pad_square`. Использовать ограниченный интерпретатор декларативных операций torchvision/Pillow с parity-проверкой против официального примера; неизвестные операции отклонять. Веса не скачиваются для чтения одного профиля.
- WD: строить профиль из `pretrained_cfg` через timm resolver и явного существующего WD preprocessing, включая белый square padding и прежнюю перестановку каналов. Это совместимый профиль семейства, а не общий default для всех моделей.
- Не делать fallback с AnimeTimm на WD при отсутствии файла. Для неизвестного семейства без полного поддерживаемого профиля возвращать конкретную ошибку.

Размер модели хранится полностью, даже если все известные сейчас примеры квадратные. Ограничения конкретной архитектуры проверяются отдельно; возможность представить прямоугольный профиль не обещает, что любая архитектура его принимает.

Карточки [ConvNeXtV2 Huge](https://huggingface.co/animetimm/convnextv2_huge.dbv4-full) и [CAFormer B36](https://huggingface.co/animetimm/caformer_b36.dbv4-full) используют `preprocess.json`, RGB и ImageNet-нормализацию, с выходами 512×512 и 384×384. Прямое чтение raw `preprocess.json` через доступный web-инструмент не удалось; конкретную JSON-схему необходимо взять из разрешённого Hub-доступа при реализации и сохранить небольшие fixtures. Комментарии в карточке не заменяют этот файл.

Альтернатива — брать только `input_size` timm — недостаточна для воспроизведения опубликованной цепочки AnimeTimm. Полная зависимость от `dghs-imgutils` пока не нужна: небольшой поддерживаемый набор операций можно проверить против него без замены PyTorch ComfyUI.

### 3. Один владелец preprocessing

Callable `ImageTransform` принимает исходный PIL и сам выполняет весь профиль, включая RGB/RGBA, padding и цветовые каналы. Удалить внешние безусловные square/BGR операции из `tag_image` и `RegionTagger`; оба вызывают один helper подготовки и проверки tensor. Загрузчики notebook и ComfyUI получают тот же профиль через общий загрузчик ресурсов. Сам forward по-прежнему возвращает logits и получает один sigmoid; ширина результата проверяется перед `get_tags`.

Сохранить сигнатуры публичного `tag_image` и формат результата `BatchTagging`. Для переданных вручную legacy transforms без нового профиля предоставить изолированную WD-обёртку прежнего поведения, маркированную совместимостью; не распознавать семейство по размеру tensor. Новые runtime всегда содержат профиль. Категории и порядок берутся из собственного CSV; дополнительные threshold-колонки допустимы, но не меняют пользовательскую политику.

Альтернатива — флаг BGR во всех вызывающих функциях — распространяет модельные условия по нескольким путям и не исключает двойной padding.

### 4. Комплект ресурсов и совместимый кэш

Один загрузчик определяет обязательные файлы по профилю, использует один доступный формат весов и сохраняет config/CSV/preprocess и сведения о repo ID/revision. Новые кэши размещаются с namespace полного repo ID. Старые директории `models/taggers/<basename>` остаются читаемыми для известных WD aliases; произвольному совпадающему repo ID их не назначать.

Сеть разрешена только при действующей настройке скачивания. Не расширять offline-запрет ComfyUI на существующий notebook API отдельным несовместимым изменением. Готовый локальный комплект не инициирует Hub-запросов. 401/403/gated не трактуются как необязательный файл; 404 допускается только для явно необязательного ресурса. Использовать стандартную авторизацию huggingface_hub без хранения token в отчётах.

`WDModelLoader.IS_CHANGED`, `comfy_evidence.model_identity` и `RegionTagger.identity` включают все действующие файлы и fingerprint профиля. Изменение preprocessing инвалидирует исходные оценки, изменение порогов оставляет существующее повторное применение фильтров. Метаданные загрузчика показывают repo ID, форму и источник профиля; сериализованное происхождение не зависит только от `repr(transform)`.

## Risks / Trade-offs

- Gated-модели → понятная диагностика и документированный вход Hugging Face; при невозможности скачать контрольные веса не выдавать fixture-тест за real-model smoke.
- Тяжёлые Huge/Giant модели → загружать по одной, не скачивать весь zoo; интеграционные прогоны явно фиксируют устройство и память, без обещания вместить всё в GPU.
- Расхождение операций → эталонные цветные/прямоугольные/RGBA fixtures и сравнение с официальным preprocessing; одного совпадения размера недостаточно.
- Неполная видимость Hub API при планировании → manifest собирается из доступных первичных источников и сверяется при реализации; неподтверждённая совместимость не объявляется проверенной.
- Legacy transforms → отдельные проверки старого вызова и загруженного WD; отсутствие двойного square/BGR подтверждается по tensor, а не только по списку тегов.

## Migration Plan

Сначала добавить resolver и профиль с fixtures, затем переключить оба загрузчика и все пути подготовки, затем включить расширенный каталог и UI. Старые aliases, `WDV3_MODEL` и return shape сохраняются. Новые namespace-кэши не перемещают и не удаляют существующие веса. При откате прежний код использует старые каталоги; новые ресурсы остаются отдельными. Документация явно отличает поддержку профиля, проверку загрузки и реальный inference на конкретных весах.
