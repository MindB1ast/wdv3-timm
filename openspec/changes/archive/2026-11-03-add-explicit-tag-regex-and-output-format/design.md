# Design

## Context

См. мотивацию в `proposal.md`. `parse_tags` канонизирует пробелы и делит строку по запятым/переводам строк. `DetectorConfig`, `Scripts/preprocess.py` и `comfy_evidence.py` используют буквальные множества в нескольких местах: простая замена только одного фильтра оставит обходы при merge. `collect` сохраняет сырые оценки и кэширует геометрию независимо от правил; `apply_filters` выполняет постобработку. `format_result` строит исторические `caption`/`taglist` с `, `; `formatted_text` выбирает представление и экранирует скобки. `Save Result` без `tags` сейчас читает `taglist` напрямую и теряет часть настроек вывода.

В рабочем дереве уже есть изменения нод и frontend. Реализация должна интегрироваться с ними, сохраняя посторонние изменения.

## Goals / Non-Goals

**Goals:** один контракт сопоставления для политики, независимый от форматирования текста; отсутствие неоднозначности между литералами и шаблонами; воспроизводимость через API и конфиги.

**Non-Goals:** regex-замены и генерация тегов из шаблона, изменение оценок модели, новые операции детекции, свободный текст VLM, расширение notebook UI, настройка сортировки и весового синтаксиса промпта.

## Decisions

### 1. Отдельные поля вместо встроенного синтаксиса regex

Сохранить существующие буквальные поля. Добавить поля типа list[str] в конфиге и многострочные поля в UI:

| Буквальное поле конфигурации | Regex-поле |
| --- | --- |
| `remove_tags_from_full` | `remove_tags_from_full_regex` |
| `remove_tags_from_region` | `remove_tags_from_region_regex` |
| `exclude_from_region` | `exclude_from_region_regex` |
| `only_from_source` | `only_from_source_regex` |
| `allowed_tags` | `allowed_tags_regex` |
| `full_image_only_tags` | `full_image_only_tags_regex` |
| `options.remove_tags` | `options.remove_tags_regex` |

Regex-поля не использовать для `add_tags_to_region`, `prefix_tags`, `suffix_tags`: эти операции создают конкретные имена. Альтернативы `re:...`, `/.../` и общий переключатель режима отвергнуты: они меняют смысл допустимых буквальных тегов либо мешают смешивать оба вида правил.

В UI regex разбирается только по переводам строк. Пустые строки игнорируются; содержимое непустого шаблона, включая пробелы, запятые и обратные слеши, сохраняется. Обычные списки продолжают использовать `parse_tags`. Подсказки должны приводить примеры `blue eyes, long_hair` и regex `.*_eyes`, указывать `tag:score` для ручных добавлений и отсутствие regex в них.

### 2. Единое сопоставление с каноническим именем

Использовать Python `re` и `fullmatch`, с учётом регистра, без автоматической замены пробелов или флагов. Inline-флаги Python разрешены. Шаблоны компилировать один раз на применение политики; ошибки валидировать также при загрузке/сохранении конфигурации. Диагностика содержит поле, индекс шаблона с 1 и имя источника при наличии. Не распознавать regex по содержимому буквального поля.

Общая операция проверки возвращает совпадение и сведения о буквальном/regex-правиле. Передать её во все места проверки членства, включая merge, ручные добавления, владение и причины решений. Литералы и regex одного действия образуют объединение. Для белого списка отдельно хранить признак активности: заданный regex без совпадений не эквивалентен отсутствию ограничения.

Владение разрешать по конкретному имени тега среди всех источников; совпадения нескольких владельцев допустимы. Учитывать имена ручных добавлений наряду с модельными тегами, чтобы prefix/suffix не обходили владение. `full_image_only_tags=None` сохраняет исторический набор композиционных ограничений, явный `[]` отключает его; regex дополняет выбранный буквальный набор. Ratings не включать в новые regex-операции general/character.

Сохранить существующий порядок политики: пороги, региональные удаления/добавления и белый список, merge с подтверждением/композицией/владением, глобальные добавления и удаления, финальная проверка владения. Regex не даёт исключений из этих ограничений. В decisions добавить сведения о совпавшем правиле, сохранив существующие reason и score. Viewer/Inspect показывает их как текст.

### 3. Разделитель применяется только при окончательном форматировании

Добавить `options.tag_separator: str`, default `, `, только в Tagging Settings. Все общие настройки тегирования и вывода, включая SAM batch, передаются в Tag Image / Regions через `options`; сама нода показывает только подключения данных и моделей. Без options используются defaults. Старые прямые Python-вызовы сохраняются как совместимый API без публикации локальных параметров в UI. При открытии старого UI-workflow локальные настройки переносятся в отдельную Tagging Settings, если options не был подключён. Поле разделителя принимает фактическую строку дословно, включая пустую и пробельную; escape-последовательности вроде двух символов `\n` специально не декодируются. Произвольная строка может включать несколько символов.

Сохранить внутренние `caption`/`taglist` как совместимые исторические представления. Получать упорядоченные имена из канонического результата до соединения, затем применять замену `_`, экранирование скобок к каждому тегу, затем `join(tag_separator)`. Не пытаться разобрать окончательную строку по пользовательскому разделителю: он может совпадать с частью имени.

Использовать единый formatter для `outputs`, прямого тегирования, Tag Folder, viewer/Inspect, Export Report и Save Result без `tags`. Канонические словари и порядок остаются источником данных; `settings.options` переносит разделитель и остальные параметры. Явный `tags` сохранять дословно. Для JSON старого формата без настроек оставить fallback на `taglist`/`caption`. Сравнение настроек при Merge Results учитывает default разделителя, поэтому отсутствие поля совместимо с явным `, `.

Альтернатива менять разделитель во всех `caption`/`taglist` отвергнута: существующий код использует эти строки с фиксированным синтаксисом для восстановления порядка. Границы изображений в отчёте не зависят от разделителя внутри подписи.

### 4. Совместимость и кэш

Добавление полей в schema_version=1 обратно совместимо для нового reader: отсутствующие regex дают `[]`, отсутствующий разделитель даёт `, `. Старый reader может отклонить новый конфиг — это документируется. Импорт старого `detectors.json` и пресеты должны очищать отсутствующие regex-поля выбранной ноды, чтобы не оставлять предыдущие скрытые ограничения; соседние ноды не меняются.

Regex и разделитель — параметры политики/представления, не геометрии или модели. Не добавлять их в ключ сырого evidence; изменение правил вызывает только повторную фильтрацию. Сохранить исходные оценки и старую публичную сигнатуру notebook-вызовов.

## Risks / Trade-offs

- Больше полей в ноде → сгруппировать regex как дополнительные настройки, явно подписать соответствующее действие; импорт и пресеты переносят оба вида полей.
- Regex с чрезмерным backtracking может замедлить обработку → компилировать вне циклов тегов, сопоставлять только короткие имена; не обещать timeout стандартного `re`. Отдельный движок с timeout вне этого change.
- Разделитель-пробел при замене `_` даёт неоднозначный для обратного разбора текст → словари JSON остаются каноническими, итоговый текст не разбирается обратно.
- Несогласованность фильтра, merge и диагностики → общие операции сопоставления и проверки на конфликты политик, включая ручные теги.

## Migration Plan

1. Добавить совместимые defaults, matcher и formatter, затем связать с UI, экспортом и конфигами.
2. Проверить старые workflow/пресеты и API на неизменность результата при defaults.
3. Обновить подсказки, документацию и примеры, выполнить профильные проверки.
4. Откат: вернуть прежнюю версию и использовать старые пресеты; для нового пресета сначала удалить regex-поля и `tag_separator`. Потерю regex-политики при таком удалении явно учитывать.
