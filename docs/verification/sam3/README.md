# Приёмка SAM 3

Проверки выполнены 2026-10-30 на Windows. Это отчёт реализации общего пайплайна и протокола. Настоящий Transformers SAM CPU inference проверен на небольшой случайно инициализированной архитектуре. Пользователь подтвердил работоспособность полного checkpoint; четыре завершённых CPU-запуска зафиксированы в `user-cpu-runs.json`. Native GPU inference ещё не проверен.

## Воспроизведение

Из корня проекта:

```powershell
$env:YOLO_CONFIG_DIR = (Join-Path (Get-Location) 'temp/yolo-settings')
temp/apply-runtime/Scripts/python.exe audit/run_checks.py --report docs/verification/sam3/tests311.json
.venv/Scripts/python.exe audit/run_checks.py --report docs/verification/sam3/tests312.json
temp/apply-runtime/Scripts/python.exe audit/check_types.py --report-dir docs/verification/sam3/types311
.venv/Scripts/python.exe audit/check_types.py --report-dir docs/verification/sam3/types312
openspec validate add-sam3-regional-tagging --strict
git diff --check
```

`tests311.json` и `tests312.json` содержат результаты по каждой проверке, включая старые контракты. Типовые отчёты отдельно фиксируют отсутствие ошибок корректных потребителей, три ожидаемые ошибки legacy-потребителя и две ошибки SAM-потребителя. SAM-зависимости для этих проверок не нужны.

Итог после добавления auto/CPU и исправления просмотра масок/Jupyter: **108/108** проверок на Python 3.11 и **108/108** на Python 3.12, без пропусков. Положительные типовые контракты проходят; отрицательные дают ровно ожидаемые 3+2 диагностики. `openspec validate --strict` и `git diff --check` проходят.

Просмотр масок: исходный RGB остаётся единственным image trace, маски — скрытые PNG с alpha и непрозрачностью 30%. Регрессии проверяют отсутствие масок в YOLO-only фигуре, неизменные пиксели статического экспорта, скрытое начальное состояние и сохранение обработчиков в HTML/Jupyter. Выбор маски использует координаты курсора и минимальную площадь SAM bbox вместо результата Plotly hover, зависящего от наложения traces. Настоящее наведение в браузере в этой среде не проверено.

`node --test audit/test_region_hover.cjs`: **7/7** проверок реального JavaScript-обработчика с двойниками DOM/Plotly. Проверены три вложенных рамки при обоих порядках отрисовки, частичное пересечение и равные площади, переходы между областями без Plotly hover-событий, zoom/reversed Y/CSS scale, clipping, отсутствие выбора в соседнем subplot инспектора, скрытие при уходе/drag, отсутствие повторного relayout внутри одной области и пересчёт при панорамировании под неподвижным курсором.

Jupyter-вывод SAM изолирован в `srcdoc` iframe с собственной копией Plotly; под ним остаётся обычный PNG исходного кадра на случай отсутствия выполнения JavaScript. Регрессия разбирает HTML и проверяет PNG-пиксели, отсутствие скриптов в родительском выводе, изоляцию iframe и обработчики внутри него. Оба изображения инспектора передаются как PNG; побайтовая геометрия и RGB-пиксели кадра/WD-вырезки проверены в обоих режимах. Это автоматические проверки разметки и данных; отображение в конкретном клиенте Jupyter пользователя ими не подтверждено.

Исправлен случай передачи SAM-конфига в `detectors_config`: ошибка теперь указывает `sam_config` до скачивания/загрузки моделей. Для native safetensors проверены точные значения весов, префикс `detector.`, отсутствие скачивания и строгий отказ на недостающие ключи/неверные размеры. Пользовательский `models/sam3/model.safetensors` имеет ключи Transformers: теперь `backend=auto` направляет его в Transformers. Его веса не изменялись.

`device=auto` проверен для CPU, доступной CUDA и неработающего драйвера; явное недоступное устройство отклоняется. Проверены текущий Python по умолчанию, локальный/репозиторный model source, offline-режим и выбор только недостающих файлов без перезаписи существующих весов/конфигов.

Реальный API-прогон: [transformers-cpu-smoke.json](transformers-cpu-smoke.json). Используются настоящие `Sam3Model`, `Sam3Processor`, safetensors и worker; два разных размера изображений, два текста, сравнение B=1/2. Архитектура уменьшена до десятков каналов и одного слоя, веса случайные. Это проверка интеграции и строгой загрузки, не доказательство качества/скорости полного `unsloth/sam3.1`.

```powershell
temp/sam-transformers-runtime/Scripts/python.exe audit/run_sam_transformers_smoke.py --report docs/verification/sam3/transformers-cpu-smoke.json
```

Тестовое окружение содержит отдельные зависимости из `requirements-sam-transformers.txt`; torch и зависимости WD переиспользованы через локальный `.pth` из `.venv` только для этого прогона. Базовые `.venv` и Python 3.11 не обновлялись. В доступной среде наблюдалось около 0.5 GB свободной памяти, поэтому полный пользовательский файл (около 3.4 GB одних FP32-весов) здесь не загружался. Это ограничение проверки, а не CPU-backend.

Новые проверки охватывают:
- Конфиги, типы, минимальный bbox крайнего пикселя, отверстия/раздельные компоненты, EXIF, padding и точный RGB-вход.
- Настоящий локальный JSONL subprocess с тестовым исполнителем: версия/request/image/source IDs, повреждённые ответы, размеры/пути масок, неполные результаты, stderr, timeout, OOM-диагностика и отмена.
- Контракт backend SAM с CPU-двойниками: один visual image batch для нескольких кадров, разные prompts без смешения состояния, декодирование logits в вероятности и разные размеры выходных масок. Это не проверка upstream SAM с реальными весами.
- Настоящие WD tensors с B>1, разные строки, неполный batch, YOLO/SAM-ветви, фильтры и отсутствие автоматического тега из prompt.
- Перенос lossless экспорта, checksums, повторная подготовка/тегирование без SAM, неизменность масок, сохранность исходных TXT, отказ записи маски и сохранение завершённых изображений при отмене.
- Повторный рекурсивный запуск без включения собственных экспортов и одинаковый fingerprint при смене разбиения на batch.
- Статический/интерактивный просмотр обоих режимов и исполняемый пример без VLM/ComfyUI.

При параллельных прогонах наблюдался разовый Windows `WinError 5` на замене manifest. Добавлен ограниченный повтор только ошибок доступа/совместного использования Windows (до пяти попыток, суммарная задержка не больше 0.5 секунды). Постоянная ошибка по-прежнему останавливает запуск; проверка отказа записи не ослаблена.

## Незавершённая GPU-приёмка

Открыты задачи `5.3`, `7.2` в `add-sam3-regional-tagging`:
- Задача `3.5` завершена: image batch, команды load/offload и повторные порции проверены на фиксированной Transformers 5.22.1; native backend дополнительно проверен контрактными двойниками. Конкретная GPU-ревизия native SAM ещё не проверена с весами.
- Попеременная выгрузка моделей реализована, но реальный peak GPU memory и отсутствие одновременного удержания SAM/WD ещё не измерены.
- Сравнение реального SAM batch=1/batch>1 и обоих режимов ещё не выполнено. Качество сегментации и улучшение тегов не заявляются.

В доступных интерпретаторах установлен CPU PyTorch; совместимый native SAM checkpoint не предоставлен. Для завершения нужен Python отдельного окружения с совместимым CUDA torch, доступная NVIDIA GPU и checkpoint SAM 3 с разрешённым доступом. Текущее WD-окружение и его pins автоматически не заменялись.

Подготовлен `examples/sam3_smoke.py`: он выполняет четыре реальных запуска (`mask`/`bbox`, batch=1/2), требует минимум два изображения разных размеров и несколько prompts, сохраняет версии/хеши/метрики памяти. Маски и bbox сравниваются точно, состав тегов — точно, scores — с `rtol=1e-4`, `atol=1e-5`. Отсутствующее окружение или пустая сегментация всего набора не дают успешную приёмку.

```powershell
python examples/sam3_smoke.py ./pictures --sam-python ./temp/sam3-runtime/Scripts/python.exe --sam-config ./sam_sources.example.json --output ./temp/sam3-gpu-acceptance
```

После успешного прогона необходимо зафиксировать SAM commit/tag и checkpoint hash, приложить `smoke.json` и закрыть задачи GPU-приёмки. До этого GPU-поддержка не считается проверенной.

## Дополнение: пользовательские CPU-запуски и lifecycle

В `region_runs/` найдены четыре экспорта со статусом `complete`, по четыре
завершённых изображения в каждом. Они используют полные веса `unsloth/sam3.1`,
Transformers 5.22.1, Python 3.12.15 и torch 2.6.0+cpu, SAM batch=1 и WD region
batch=8. Контрольная сумма весов:
`28cd71c60e3034fc05ab67aa6b960d5340087fc72e456f2989b50294dd6b4dc9`.
Пользователь сообщил, что запустил SAM и видит рабочий результат. Сводка
`user-cpu-runs.json` сохраняет provenance, хеш каждого manifest и диагностику
каждого изображения. Исходные экспорты не изменялись. Это подтверждение полного
CPU-сценария; сравнений SAM batch=1/2 и измерений GPU memory в этих запусках нет.

Добавлены явные `load`/`offload` в клиент и worker. Загрузка возвращает на
устройство уже созданную модель без чтения checkpoint. После сегментации
оркестратор ждёт подтверждения offload, прежде чем возвращать WD на устройство.
Embeddings, predictions и генератор кандидатов освобождаются также при ошибке
декодирования. Регрессии проверяют освобождение через weakref, повторную порцию
после ошибки, независимые prompts/пустые ветви и порядок SAM/WD на двух порциях.

Дополнительные отчёты: `lifecycle-tests312.json`, `lifecycle-types312/summary.json`
и `lifecycle-transformers-cpu-smoke.json`. Последний использует настоящую
Transformers 5.22.1 с небольшой архитектурой, B=1/2, двумя prompts и командами
load/offload в одном worker. Двойники и маленькая модель не заменяют GPU-приёмку.

Результат: **110/110** регрессионных проверок, без пропусков; положительные
типовые контракты без ошибок, отрицательные — ожидаемые 3+2 диагностики.
Настоящий Transformers worker прошёл load/offload roundtrip, сравнение B=1/2 и
строгий отказ на неполные веса. `openspec validate --strict` и `git diff --check`
проходят. Реализация переключения SAM/WD завершена; checkbox `5.3` остаётся
открытым только из-за требуемого измерения на настоящем GPU. `7.2` также
требует GPU: обычный успешный CPU-запуск не содержит этих измерений.

Пользователь уточнил: используется ноутбук с видеокартой не NVIDIA, возможности
выполнить CUDA-приёмку нет. Рабочий сценарий пользователя — Transformers SAM 3.1
на CPU, подтверждённый перечисленными выше полными запусками. Задачи `5.3` и
`7.2` сохраняются незавершёнными в части GPU-измерений; это ограничение приёмки
CUDA, а не отказ CPU-сценария. Проверенность CUDA и других GPU backend не заявляется.
