# Локальная постобработка тегов

Порядок новой ветки: **Collect Evidence → Filter Tag Sets → операции → Merge
Tag Sets → Inspect / Export Report**. Результат merge по-прежнему является
общим описанием полного изображения с деталями от детекторов.

Filter Tag Sets использует существующие options и правила источников. Сначала
применяются пороги, локальные remove/add/allowed. Полный кадр и каждый регион
сохраняют отдельные принятые general/character, исходные raw_scores, ratings,
геометрию, идентичность и причины решений. Политики владения, композиционного
допуска, удаления из full и подтверждения полным кадром применяются при merge.
Для подтверждения используется **обработанный набор full**, а не его raw.
Глобальные prefix/suffix/remove и формат текста также остаются у merge.

Старый Apply Filters — совместимое сокращение Filter Tag Sets → Merge Tag Sets
без операций. Старые Tag Image / Regions, Tag Folder и notebook-вызовы не
включают очистку автоматически. Изменение локальных операций не запускает
модели повторно при доступных evidence; постоянное хранение после перезапуска
добавляется отдельным change.

Здесь «при доступных evidence» означает, что готовое значение уже передано
операции. Это не гарантия, что повторный Run сохранит весь расчёт в памяти:
ComfyUI может вытеснить upstream-результаты, а внутренняя память Collect Evidence
принадлежит объекту WD-модели и теряется при его повторной загрузке. Текущая
ветка не предоставляет переключателей reuse/reuse_only/refresh или загрузки
evidence с диска. Для них предназначен отдельный change
`add-persistent-evidence-and-caption-file-workflows`. Collect Evidence существовал
до добавления локальной постобработки и здесь используется как её вход.

## Контракт Python / JSON

`Bundle(kind='tag_sets', schema_version=1)` — неизменяемое JSON-значение.
`data()` возвращает отдельную копию. Типы `TagSetPayload`, `LocalTagFrame` и
`LocalTagRecord` описаны в `Scripts/tag_postprocessing.py`.

- `frames`: полный кадр и `detectors[source][region_index]`, с `region_id`,
  bbox/масками и исходными пикселями для Inspect. Идентичность региона —
  `(image_id, source, region_id)`, а не один порядковый номер.
- `evidence`: исходный переносимый Bundle с полными оценками и геометрией.
- `postprocessing`: упорядоченная нормализованная спецификация операций.
- `postprocessing_history` каждого выбранного локального набора: before/after,
  входной/выходной digest и все удаления с правилами и свидетелями.

Ниже код внутри пакета расширения; `evidence` уже получен от Collect Evidence:

```python
from .comfy_evidence import filter_tag_sets, merge_tag_sets
from .Scripts.tag_postprocessing import remove_redundant

tag_sets = filter_tag_sets(evidence)
cleaned = remove_redundant(tag_sets, {
    'explicit_enabled': True,
    'relations': [{'specific': 'miniskirt', 'general': 'skirt'}],
    'scope': 'regions',
    'sources': ['clothes'],
})
result = merge_tag_sets(cleaned)
```

`Bundle.from_json(tag_sets.to_json())` восстанавливает значение без моделей.
Работать с тегами нужно до merge, а не удалять их из уже плоского caption.

## Remove Redundant Tags

### Regex-семейства вместо перечисления пар

Включите `regex_enabled` и заполните **regex_relations_json**:

```json
[
  {
    "id": "colors_to_base",
    "specific": "(?:black|white|red|blue)_(?P<base>.+)",
    "general": "\\g<base>"
  },
  {
    "id": "skirt_lengths",
    "specific": "(?:mini|micro)(?P<base>skirt)",
    "general": "\\g<base>"
  }
]
```

Первое правило покрывает black_skirt→skirt, white_dress→dress и другие
выбранные цвета без отдельных пар на каждый тег. Второе — miniskirt→skirt и
microskirt→skirt. `(?P<base>...)` захватывает имя, `\g<base>` подставляет его;
внутри JSON обратный слеш удваивается. `general` — **шаблон подстановки**, не regex
для поиска произвольного другого тега. Можно использовать и постоянное имя.

`specific` сопоставляется через Python regex fullmatch с полным принятым именем
с `_`, без нормализации шаблона. Развёрнутое общее имя канонизируется как один
буквальный тег. Оно удаляется только при наличии в том же general-наборе.
Ничего не добавляется. Самосовпадение игнорируется. Защита и scope действуют
как у других методов. Непринятый конкретный тег не является свидетелем.
Циклические отношения на фактическом наборе отклоняются без изменения исходника.

Regex-поля независимы: `relations_json` остаётся буквальным, а textual_enabled
не нужен для regex. Общие шаблоны — пользовательская политика, а не готовая
семантическая онтология; незнакомые связи вроде miniskirt/skirt без подходящего
шаблона сами не угадываются.

Для переноса в Postprocessing Config используйте в операции `regex_enabled: true`
и `regex_relations: [...]` с тем же массивом. Старые настройки без этих полей
означают False/пустой список. В workflow новые виджеты добавлены после старых.
В истории каждого удаления сохраняются id, pattern/template, свидетель и
`rule_digest`. Полный снимок правил находится в цепочке: будущий агент может
сравнивать версии и переигрывать их без инференса. Агентная генерация правил
этой операцией не запускается.

Все три способа выключены по умолчанию и меняют только general. Character, ratings,
raw_scores, геометрия и модельные оценки оставшихся тегов сохраняются.

- `explicit_enabled`: точные пары из `relations_json`, например
  `[{"specific":"miniskirt","general":"skirt"}]`. Это означает удалить skirt,
  **только если оба тега приняты в одном наборе**. Отсутствующие теги не добавляются.
- `textual_enabled`: отдельная эвристика по последовательностям целых компонентов
  имени: black_skirt может вытеснить skirt, но skirted — нет. Это не знание
  смысла тегов; используйте явные пары для контроля семантических связей.
- `protected_tags`: буквальные теги через запятые/переносы; защищены от всех методов.
- `scope`: full, regions или all; `sources`: имена региональных источников через
  запятые/переносы, пусто — все. Имена источников сохраняют пробелы. Неизвестный
  источник вызывает ошибку до применения операции; существующий пустой — допустим.

В именах тегов `black skirt` = `black_skirt`. В буквальном `relations_json` каждая
сторона — одно полное буквальное имя. Regex и поиск подстрок в этом поле не выполняются.
Поэтому explicit-пара miniskirt→skirt не затрагивает неизвестный составной тег
лишь из-за слова skirt в его имени. Циклы и самоссылки в таблице запрещены.

Все удаления одной операции вычисляются по одному входному снимку. При входе
a,b,c и парах a→b, b→c удаляются b и c; свидетель удаления c — входной b.
Порядок строк не меняет результат. Последующие ноды работают по выходу предыдущих.
Все совпавшие причины сохраняются; тип решения — `redundant_tag`.

Операция **не сравнивает разные регионы или full с регионом**. Если full содержит
skirt, а регион — miniskirt, общий caption может сохранить оба. Отсечение full
задаётся существующими правилами источников отдельно. Два региона с 1girl остаются
двумя локальными наборами; допуск 1girl в общий caption определяется композицией.

Для отмены обойдите ноду или отключите все способы. Исходные evidence сохраняются.
Merge Results принимает одинаковые цепочки и повторяет их после объединения
evidence; разные цепочки отклоняются. Это исключает скрытое восстановление
удалённого тега при повторной фильтрации ветвей.

## Перенос цепочки через пресет

Для работы на canvas достаточно отдельных нод операций: их виджеты сохраняются
в workflow. Для независимого pipeline-пресета добавьте **Postprocessing Config**:
он принимает JSON-описание упорядоченной цепочки и не требует evidence/изображений.
Подключите `postprocessing` к Save Pipeline Config. Выход `postprocessing`
Load Pipeline Config подключается к одноимённому входу Filter Tag Sets.
Числовые настройки тегирования остаются в Tagging Settings, а операция не
дублируется виджетами в Tag Image / Regions.

Пример значения `postprocessing_json`:

```json
[
  {
    "schema_version": 1,
    "operation": "remove_redundant",
    "explicit_enabled": true,
    "textual_enabled": false,
    "relations": [{"specific": "miniskirt", "general": "skirt"}],
    "protected_tags": [],
    "scope": "regions",
    "sources": []
  }
]
```

Настройки конфигурации хранятся под `postprocessing`, отдельно от `options`;
история вычислений в них не записывается. Старый пресет без поля возвращает
пустую цепочку. Существующий Python `config_values` сохраняет прежний кортеж
из четырёх элементов; цепочка доступна отдельно в валидированном JSON.

Упорядоченное описание фактически применённых операций также сохраняется в
`results_json.settings.postprocessing`. Его можно перенести в конфигурационную
ноду. Если цепочка уже подключена к Filter Tag Sets, дополнительные operation-ноды
после него означают ещё один явный шаг, а не замену сохранённой цепочки.

## Проверка результата

Подключите `tag_sets` после операции к одноимённому входу Inspect. Выберите регион:
в нём доступны before/after, исходные вероятности, `redundant_tag`, метод и
тег-свидетель. Для общего caption используйте Merge Tag Sets → results у Inspect.
HTML/JSON по локальной стадии можно экспортировать с выключенным save_txt:
до merge общего caption ещё нет. TXT сохраняется из результатов после merge.

Проверяемый пример: `examples/comfyui_wdv3_postprocessing.json`. Он содержит
отдельные Inspect для локальных наборов и общего описания. Пример использует
реальные настроенные модели при пользовательском запуске; автоматическая
приёмка отдельно использует фиксированные evidence и запрещённые loaders.
