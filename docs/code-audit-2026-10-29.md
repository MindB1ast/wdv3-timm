# Ревизия перед расширением ComfyUI

Дата: 2026-10-29. Проверены структура Python-кода, объединение, фильтры, обработка изображений, файловый экспорт, метрики, notebook-вход и статические замечания. После первоначального обзора ревизия расширена с использованием выбранного пользователем `ub-mode`. Рабочие исходники не исправлялись; добавлены отдельные проверки и отчёт. Все архитектуры WD, GPU, ComfyUI и качество на независимом датасете в этот аудит не входят.

## Итог проверки до изменений

**Пайплайн запускается, но считать его корректным во всех проверенных сценариях нельзя.** Свежий CPU-прогон обработал 5/5 изображений; объединённые теги и scores совпали с первым прогоном. Проверки поведения: 30 выполнено, 18 прошло, 11 завершилось assertion failure и 1 — NameError в рабочем коде, skipped=0. Это 12 нарушенных контрактов, часть из них связана с общими причинами.

Особенно важно исправить перезапись существующей подписи при ошибке чтения в append-режиме до массового запуска с сохранением. До расширения в ComfyUI нужны небольшие исправления сохранения, объединения и согласованности данных. Исправления в рамках этой ревизии не выполнялись.

SHA-256 до и после совпали для всех 18 защищённых файлов: 12 модулей Scripts, detectors.json, requirements.txt и 4 исходных TXT. Базовый Git commit: `e6fa7571dc51773003916caaf13ff22412096c77`. В начале уже имелись неотслеживаемые `.agents/`, `openspec/`, `docs/`; они не удалялись. Новые диагностические файлы находятся в `audit/` и `docs/audit/2026-10-29/`.

## Что ещё требует проверки

- `Scripts/main.py:179–219`: финальное добавление/удаление меняет текстовые поля без соответствующего обновления score-словарей.
- `Scripts/analitycs.py:48`: оценка использует только пересечение обработанных изображений с эталонами; пропуски могут остаться вне метрики. Идентификация по имени без каталога может смешать изображения.
- `Scripts/analitycs.py:73–76`: исторический F1 — гармоническое среднее усреднённых precision/recall, а не samples F1; его нужно явно отличать при сравнении экспериментов.
- `Scripts/model.py:77`: путь локальной загрузки сначала создаёт модель через HF Hub; офлайн-поведение требует отдельной проверки.
- `Scripts/main.py` не использует `opts.batch` для реального пакетного инференса; большие try/except и print затрудняют определение полноты обработки.
- `Scripts/savingProc.py` и `tag_manager.py`: проверить сохранность существующих подписей при сбоях чтения/записи до подключения массового экспорта.

Большинство пунктов выше теперь подтверждено проверками в предыдущем разделе. Историческая формула F1 — явно выбранная формула, а не сама по себе доказанный вычислительный баг. Офлайн-путь ViT с имеющимся HF-кэшем работал; загрузка только из отдельной локальной папки без HF-кэша не проверялась. Параметр batch, ошибки записи после открытия файла и частичная загрузка детекторов требуют дальнейшей проверки. При пустой детекции также наблюдалось ResourceWarning о незакрытом PIL-файле; это отдельно от 12 нарушенных контрактов.

Эти количества не являются количеством функциональных багов. Сначала разбирать подтверждённые ошибки, затем значимые предупреждения; стиль исправлять отдельными небольшими изменениями. Не считать максимальный балл линтера критерием правильности тегирования. Для новых изменений разумно контролировать отсутствие новых ошибок относительно исходного состояния, не скрывая существующие замечания глобальными отключениями.

## Журнал ревизии

1. Прочитаны исходный SKILL.md ub-mode и инструкция skill-installer; выбранный навык установлен, зафиксирована граница проверки без исправлений.
2. Зафиксированы Git HEAD, начальное состояние и SHA-256 защищённых файлов, чтобы проверить сохранность исходников и подписей.
3. Прочитаны экспорт, метрики, загрузка моделей и постобработка; добавлены 18 проверок рабочего поведения и 12 контрактов на обнаруженные нарушения.
4. Первый запуск выявил дополнительно ошибку очистки временного файла в тестовом окружении Windows; проверочный код стал явно закрывать PIL-изображение. Assertions не ослаблялись, рабочий код не изменялся. Повторный запуск оставил только ошибки проверяемого поведения.
5. Загружены закреплённые исходники crapper/dryer/mutator; установлен Python-парсер, анализ выполнен на копии Scripts в temp/audit-snapshot. Первоначальный запуск через Python -m не вызывал CLI entry point; исправлен способ запуска инструмента. Ошибка сети при загрузке парсера устранена разрешённой загрузкой в temp/parser-cache, исходники не отправлялись внешнему сервису.
6. Повторён реальный офлайн CPU-прогон WD ViT/YOLO на 5 изображениях с отдельной выходной папкой; итоговые теги и scores совпали с первым прогоном.
7. Добавлен воспроизводимый runner с JSON-отчётом; финальный итог 18 passed, 11 failures, 1 error, 0 skipped. Повторены Pylint и проверка объявленных зависимостей.
8. Сохранены отчёт и диагностические артефакты, проверено совпадение всех 18 хешей. Коммиты, push, рефакторинг и реализация нод не выполнялись.

## Рекомендуемый процесс проверки — предложение, не новая реализация

1. Формулировать ожидаемое поведение и реальные примеры до изменения кода. Для известных дефектов тест должен воспроизводить ошибку старой версии и проверять желаемое поведение; нельзя превращать старый ошибочный вывод в эталон.
2. Для merge и фильтров применять небольшие детерминированные тесты, не загружая тяжёлые модели. Проверять свойства: независимость от порядка ветвей, отсутствие дублирования, неизменность исходных свидетельств, согласованность текста и словарей.
3. Добавлять независимую приёмочную проверку. Изменения тестов и отключения проверок должны отдельно просматриваться; простое поручение «не менять тесты» не является техническим запретом. При необходимости права записи на приёмочный набор ограничиваются окружением CI.
4. Проверять силу тестов намеренными поломками поведения: возвратом перезаписи исключений, удалением персонажей из caption. Соответствующие тесты должны падать. Мутационное тестирование применять выборочно к критичному ядру, а не ради числа проверок.
5. Разделять корректность программы и качество ML: smoke-прогон проверяет работоспособность, а подтверждённый датасет с независимой итоговой частью — качество тегов. Повторно подбирать фильтры по итоговой части нельзя.
6. После функциональных проверок запускать Pylint и просматривать diff на ослабление asserts, skip/xfail, игнорирование ошибок и изменение состава оцениваемых данных. Отдельный reviewer полезен, но сам по себе независимость критериев не гарантирует.

Отказ от TDD не устраняет подгонку. В рассмотренных источниках подтверждён риск редактирования/обхода тестов агентами, но они не устанавливают, что TDD как метод в целом хуже альтернатив. Практическая рекомендация — проверяемые спецификации, независимая приёмка и несколько видов свидетельств, а не только зелёные тесты.

Источники:

- [OpenAI: How we monitor internal coding agents for misalignment](https://openai.com/index/how-we-monitor-internal-coding-agents-misalignment/) — описывает reward hacking через изменение тестов и отключение проверок; не сравнительное исследование TDD.
- [Pylint: Running Pylint](https://pylint.readthedocs.io/en/latest/user_guide/usage/run.html) — запуск и управление статическими проверками.

Рекомендуемая последовательность проекта: небольшое исправление ядра с регрессионными проверками, затем выделение этапов и реализация нод из существующего proposal. Полную косметическую перепись перед интеграцией не проводить.
